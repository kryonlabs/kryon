# Kryon website CUI parity research

Status: research and redesign specification only. No implementation, local build,
commit, push, release, or deployment was performed.

## Scope and conclusions

The owner's goal is a Kryonlabs website at least as good as
[CUI](https://yappologistic.github.io/CUI/), with CUI-like default component
appearance, then stronger customization and coverage. The owner explicitly does
not require the website's component catalog to include a live-preview editor.

The true website owner is this repository, `kryonlabs/kryon`, not
`kryonlabs/github`. The maintained website source is `docs/site/`; its build
inputs include the gallery sources and site scripts. The Cloudflare Pages
deployment defined by `.github/workflows/pages.yml` publishes the prepared
`docs/site` tree for project `kryon` from `master` under `kryonlabs.com`; this
is not a GitHub Pages deployment.

CUI looks stronger for six concrete reasons:

1. Its overview immediately proves the component system with visual examples.
2. Its documentation is dense but readable: a small UI type scale, a separate
   long-form reading scale, narrow prose measure, and compact section spacing.
3. Its surfaces are disciplined: neutral light and dark palettes, hairline
   borders, restrained radius and control scales, and shadows only on floating
   layers.
4. Its catalog is an information system, not a demo list: category counts,
   search, honest summaries, APIs, options, scenes, guides, and showcases.
5. Its navigation stays persistent and predictable while fitting both desktop
   documentation and mobile drawer patterns.
6. Its component presentation is generated by the actual system, so the page is
   product proof rather than CSS mockups.

Kryon's present site is an accessible warm editorial brochure, but not a compact
product documentation system. It uses oversized display type, a taller header,
wider gutters, decorative card shadows, generic gallery notes, and a one-at-a-
time live editor. Those choices make the product feel less systematic and less
component-rich than CUI.

## CUI design language

### Typography

| Context | Font | Size and line height |
|---|---|---|
| Site UI/body | Inter 400 | 14px / 1.55 |
| Long-form docs | Documentation body | 16px / 1.75 |
| Prose measure | Long-form text | 76ch maximum |
| General heading 1 | Geist 500 | 32px |
| General heading 2 | Geist 500 | 22px |
| General heading 3 | Geist 500 | 15px |
| Home heading 1 | Geist 500 | 56px |

Kryon should use the CUI scale for the product site even if long-form guides use
the larger reading scale. Manrope/Newsreader may remain as brand accents, but
not at the current brochure scale.

### Layout and density

| Element | CUI value |
|---|---:|
| Topbar | 56px |
| Persistent sidebar | 264px |
| Standard docs maximum width | 880px |
| Docs horizontal padding | 32–48px |
| Bottom page padding | 112px |
| Component grid | `repeat(auto-fill, minmax(230px, 1fr))` |
| Component grid gap | 14px |
| Card body padding | 12/14/14px |
| Card title | 14px |
| Card summary | 12.5px, two-line clamp |
| Compact row padding | 9/8px |
| Compact row text | 13–13.5px |

Card thumbnails are 16:9. Resting cards use hairline borders, radius 18, and no
shadow. Compact list rows omit thumbnails and expose title, summary, and API
columns.

Spacing follows a four-point grid:

- 4px micro steps.
- 16px inside a group.
- 24px between related regions.
- 32–48px between major sections.

### Radius and controls

Radius scale:

| Surface | Radius |
|---|---:|
| Marks | 6px |
| Rows/items | 8px |
| Controls | 10px |
| Panels | 14px |
| Surfaces/dialogs | 18px |

Control heights:

- Small: 30px.
- Medium: 36px.
- Large: 44px.

These website densities must not be independent CSS: they need a shared semantic
token contract with the actual Kryon widget theme. `src/ui/theme.zi` currently
uses materially different values, including 4/12/28px radii and 32/40/48px
controls.

toasts, and other floating layers cast shadows.

### Motion

| Purpose | Duration |
|---|---:|
| Highlight | 100ms |
| Hover | 140ms |
| State | 180ms |
| Enter | 260ms |
| Exit | 160ms |

Easing: `cubic-bezier(0.22, 1, 0.36, 1)`.

`prefers-reduced-motion: reduce` must disable drawer/scrim and decorative
movement.

### Responsive behavior

At widths below 860px:

- Sidebar becomes a drawer.
- Drawer width is `min(300px, 86vw)`.
- It closes on navigation, scrim press, Escape, or resizing back above 860px.
- Scrim and drawer animation are removed under reduced motion.

At widths below 640px:

- Page margins are 16–20px.
- Stage padding is reduced.
- Filter chips scroll horizontally without creating page overflow.
- Option-table rows stack.
- Component cards remain full-width with 16:9 thumbnails.

No maintained route may have horizontal overflow from 320 through 1366px.

## Kryon redesign specification

### Information architecture

Primary navigation:

1. Overview: `/`
2. Guide: `/getting-started`
3. Components: `/widgets`
4. Showcase: `/showcase`
5. Apps: `/apps`
6. Docs: `/docs`

This is the smallest stable-URL route. Add `components.html` only as an alias
or redirect to `widgets.html`; do not fork duplicate content. Redirect `/demo`
to the component catalog after migration and remove the superseded live-editor
implementation and assets once no maintained route references them.

Guide sections:

1. Getting started.
2. Layout and composition.
3. Theming and customization.
4. Component/API patterns.
5. Platform integration and renderers.
6. Design principles.
7. Performance and status.

Existing `/modules` and `/renderers` should remain reachable from Docs rather
than competing as primary navigation. Superseded URLs may redirect, but no
parallel legacy page or editor should remain merely to preserve an old route.

### Homepage anatomy

1. Compact product header, not an oversized editorial hero.
2. Above the fold: a neutral panel containing several real static component
   thumbnails, proving breadth immediately.
3. Fact strip with only reproducible Kryon facts: component count, supported
   platforms, renderer families, dependency policy, and package/runtime size if
   measured. Do not copy CUI performance claims.
4. Six-step learning path matching the primary guide sections.
5. Theme/customization proof using real generated light/dark component images.
6. Compact module coverage summary for Kryon UI, Plot, and DataViews.
7. Design principles and integration preview.

No homepage live editor or compiler iframe.

### Components page anatomy

Top:

- Title and one-sentence purpose.
- Text search.
- Category/module chips with counts.
- Grid/list toggle.
- Light/dark preview toggle where both assets exist.

Grid card:

- 16:9 generated component image.
- Component title.
- Module badge.
- Category badge.
- Two-line honest summary.
- API names when available.
- Source link.
- Keyboard note when meaningful.

Compact row:

- No thumbnail.
- Title and summary.
- Module/category.
- APIs/options.
- Source and detail actions.

Detail presentation:

- Larger light/dark generated images, initially on the same page rather than
  creating per-component routes.
- Source and source module.
- Purpose and composition notes.
- Public API names.
- Options and defaults.
- Keyboard and accessibility behavior.
- Related components.
- No parallel interactive editor route.

The catalog must not import `live-editor.js` or embed a compiler/preview iframe.

### Better-than-CUI customization page

Use real generated Ziran scenes, not CSS mockups, to demonstrate:

- Light/dark base themes.
- One intentional accent and semantic status colors.
- Radius scale changes.
- Compact/normal/dense layouts.
- Font family and scale changes.
- Border and focus-ring overrides.
- Component-specific token overrides.
- State preservation examples once hot-swappable `.zx` component contracts are
  implemented.

Theme documentation should expose one semantic token table and show the same
token names in website and widget source. Avoid presenting arbitrary CSS as if
the native widget system supports it.

### Static demo strategy

Preferred architecture:

1. Gallery sources remain the canonical component presentation definitions.
2. A Ziran catalog-shot host renders a selected scene without catalog chrome.
3. Private Xvfb/headless captures emit deterministic WebP or PNG images for
   each entry and requested theme.
4. Images are written under `docs/site/assets/components/`.
5. `gallery-data.js` records image paths, summaries, APIs, options, keyboard
   behavior, module, category, source path, and alt text.
6. `docs/site/gallery.js` renders static cards from that manifest.

Captures must use a private display, scrub inherited display/auth/session
variables, and touch only their own processes. The owner did not request visible
desktop capture or mouse control.

## Shared theme requirements for component/runtime work

The website redesign cannot be completed as isolated CSS. The parent's
component and renderer work should treat these as shared requirements:

- Actual widget defaults and website demos must consume one canonical Ziran
  semantic token contract; generated CSS custom properties are a bridge, not a
  second source of truth.
- Adopt CUI-compatible neutral light/dark surfaces.
- Use one intentional Kryon accent.
- Ensure control edges meet non-text contrast requirements.
- Move toward radius 6/8/10/14/18 and control heights 30/36/44.
- Use a four-point spacing grid.
- Preserve accessible focus and reduced-motion behavior.
- Keep component presentations small, portable `.zx` definitions so a future
  hot-swap path and static catalog can use the same source.
- Do not hardcode a separate website-only component appearance or move widget
  behavior into handwritten website JavaScript.

These requirements do not themselves define renderer internals, component APIs,
or hot-swap implementation; those remain with the sibling research tasks.
